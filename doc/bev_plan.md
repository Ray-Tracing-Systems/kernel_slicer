# План: паттерн Block Expansion Vectorization (BEV)

Рабочий документ. Ветка `bev`. Состояние на 2026-11-20: этапы 1 (ISPC, тест 030), 2 (вложенный `[[parallel]]`,
вариант II, тесты 092, 093) и 3 (tiled GEMM, тест 094) выполнены. Следующий — этап 4 (`LiteNN::*Block`).

## 0. Порядок работы над каждой фичей

1. Сначала пишется тест (или приложение) на C++: входной код для kernel_slicer, `main.cpp`, CPU-эталон.
2. Автор смотрит входной код, задаёт вопросы, просит исправить.
3. Только после согласования вида входного C++ кода фича добавляется в транслятор.
4. Тест проверяется на Slang, GLSL (если фича для GLSL) и ISPC; параллельные примитивы — на больших
   случайных размерах и многих прогонах.

Документация (`doc/concepts.md`, skill, `references/bev.md`, README) обновляется в конце, когда набор
возможностей устоится (этап 6).

## 1. Принятые решения

| Вопрос | Решение |
|--------|---------|
| Блочные операции (matmul и т. п.) | функции в пространстве имён `LiteNN` с суффиксом `Block`: `LiteNN::MatMulBlock(...)`; суффикс отличает их от функций одного потока (кооперативные векторы) |
| Типы для кооперативных матриц | fp16 на входе, fp32 в аккумуляторе |
| Back ends кооперативных матриц | только Slang (`CoopMat`, `VK_KHR_cooperative_matrix`, есть на Radeon 8060S); ISPC — векторизованная реализация; GLSL отложен до запроса пользователей |
| Вспомогательные функции в uniform-коде ISPC | генерировать uniform-перегрузки функций, вызываемых из однопоточных частей |
| `kernelBE2D_` | делаем, но отдельным этапом (этап 5) |
| Набор тестов | начинаем с минимального (T1, T2, T5, T7), остальное — по мере надобности |
| Семантика однопоточных операторов на GPU | вариант II, избыточное выполнение (раздел 3) |
| Вызов BEV-кернела в ISPC | кернел — шаблон, переопределить его нельзя; ISPC-класс содержит копию управляющей функции (`Test_BE`), где `kernelBE1D_X<N>(...)` заменён на `kernelBE1D_X(...)` сгенерированного класса |
| Размер блока | из аргументов шаблона в AST, можно писать именованную константу: `kernelBE1D_X<BLOCK_SIZE>(...)` |

## 2. Текущее состояние и найденные ошибки

Реализация: [block_expansion.cpp](../block_expansion.cpp), JSON в [template_rendering.cpp](../template_rendering.cpp)
(`SourceBE`, `SharedBE`, `ThreadSizeBE`), шаблоны `templates_slang/generated.slang`, `templates_glsl/generated.glsl`.
Тест: `apps/tests/030_block_expansion_v1` (Slang, GLSL).

Разбирается только верхний уровень тела блока: `DeclStmt` → `groupshared`, `for` с `[[parallel]]` → все потоки
с барьерами, остальное → `if(localTID == 0)`.

Найдено проверкой (блочная редукция, Slang):
- ~~`[[parallel]]` ищется поиском текста по всему `for`~~ — исправлено на этапе 1: ищется только в заголовке цикла;
  `[[parallel]]` внутри обычного цикла сейчас даёт ошибку транслятора (поддержка — этап 2).
- Локальная скалярная переменная блока (`float sum = sdata[0];`) становится `groupshared` с инициализатором —
  ошибка компиляции Slang.
- ~~Тело параллельного цикла без фигурных скобок генерируется без `;`~~ — исправлено на этапе 1.
- ~~ISPC: пустое тело кернела~~ — этап 1.
- ~~Размер блока извлекался `stoi` из текста вызова (именованная константа роняла kslicer)~~ — этап 1.
- `kernelBE2D_/3D_` есть в списке префиксов, но не поддержаны.

## 3. Однопоточные операторы на GPU: выбран вариант II

Варианты (подробно с примером — в обсуждении от 2026-11-19):
- **I, строгий**: однопоточные операторы выполняет поток 0, все локальные переменные блока — в `groupshared`,
  инициализация в потоке 0, барьер перед чтением. Обычный цикл, содержащий `[[parallel]]`, требует отдельного правила.
- **II, избыточное выполнение**: однопоточный код без записи в память выполняют все потоки группы (у каждого своя
  копия локальных переменных, значения одинаковы); под `if(localTID == 0)` уходят только записи в shared/глобальную
  память, атомики и т. п., после записи в shared — барьер. Обычные циклы с вложенным `[[parallel]]` получаются
  автоматически. Совпадает с uniform-кодом в ISPC. Отдельный случай: значение, полученное оператором с побочным
  эффектом (`idx = atomicAdd(...)`), нужно всем потокам — передаётся через `groupshared`.

## 5. BEV в ISPC

| C++ (BEV) | ISPC |
|-----------|------|
| `for(blockId ...)` | блоки по `task` / OpenMP / последовательно (по модели потоков ISPC); внутри `for(uniform uint blockId ...)` |
| `template<uint bsize>` | `const uniform uint bsize = N;` |
| массив, объявленный в блоке | `uniform T arr[N];` |
| однопоточный оператор | uniform-код: локальные переменные и циклы `uniform` |
| `for(i = a; i < b; i++) [[parallel]]` | `foreach(i = a ... b)`; общий случай — `for(int i = a + programIndex; cond; i += programCount)` |
| барьеры | не нужны |
| атомики по shared | `atomic_*_local` |
| вызов вспомогательной функции из uniform-кода | uniform-перегрузка функции |

## 7. Оптимизации (после того, как всё работает)

Только безопасные и несложные; корректность не должна зависеть от анализа, который может ошибиться.

- [ ] Барьеры: в однородном цикле с `[[parallel]]` внутри получается два барьера на итерацию (в конце тела и в начале
      следующей). Второй не нужен, если между ними нет обращений к shared memory (только локальные переменные блока).
- [ ] Регистры вместо shared memory: массив блока размера `bsize`, к которому во всех параллельных циклах обращаются
      только по индексу этого цикла (`acc[i]` в 094), принадлежит одному потоку; на GPU его можно держать в регистре
      потока, в ISPC — в varying-переменной. Условие проверяется по AST: любое другое обращение — массив остаётся
      в shared memory.
